## 普通表查询

以下均为客户端 execute/fetch 毫秒，包含驱动和网络。每行三阶段使用相同参数与数据，结果摘要一致。全部 294 次正式 SELECT 样本（2 表×3 阶段×7 案例×7 次）成功；这个零错误仅描述已完成样本。

| SQL 案例 | 单列基线 P50/P95/P99 | 联合索引 P50/P95/P99 | 覆盖候选 P50/P95/P99 |
|---|---|---|---|
| 主键 id+time | 1.719 / 1.849 / 1.867 | 2.048 / 2.299 / 2.336 | 1.846 / 2.053 / 2.073 |
| 用户+投影+时间排序 | 4.678 / 4.939 / 4.961 | 2.280 / 2.838 / 2.951 | 1.865 / 2.309 / 2.368 |
| OFFSET 800000 | 433.140 / 462.279 / 462.775 | 147.355 / 152.104 / 152.203 | 138.449 / 142.054 / 142.440 |
| 已知游标 keyset | 154.347 / 159.689 / 161.183 | 4.494 / 4.812 / 4.866 | 4.694 / 5.140 / 5.245 |
| 七月范围 COUNT/SUM | 619.246 / 655.130 / 659.946 | 659.009 / 748.153 / 761.384 | 30.552 / 31.256 / 31.407 |

游标按 `(created_at DESC,id DESC)` 稳定排序，与 OFFSET 同页 20 个 id 一致。取得随机深页前一个游标仍分别耗时 1252.542 / 267.119 / 453.838 ms；不能把已知游标查询成本说成随机跳页总成本。

实际 ANALYZE 用户投影访问算子输出：954 → 20 → 20 行；第三阶段 JSON `using_index=true`，TREE 为 covering lookup。OFFSET：1,000,000 → 800,020 → 800,020；keyset：1,000,000 → 20 → 20。这是访问算子输出×loops，不能解释为磁盘读页或把所有嵌套节点行数相加。

范围查询第二阶段仍实际选择全表扫描；第三阶段 TREE 选择 **covering index skip scan**，并非简单地使用 ix_time。当前通用解析器未将 skip scan 识别为访问算子，因此该案例汇总访问行数为 null；原始 TREE 明确记录 84,866 行。该 JSON 未给 `using_index`，所以此案例的该布尔观测为 false，不能据此否认 TREE 中的覆盖访问。展示保留两种原始证据，不补造行数或统一成预设结论。

七个暖样本的插值 P95/P99 不代表生产尾延迟；阶段固定顺序带有缓存与顺序混杂。10k smoke 普通表用户投影 P50 为 2.127 → 1.876 → 1.979 ms：覆盖候选在小数据上没有进一步降低客户端中位数，保留这个反例。

## 分区对照

两表都使用 PK(id,created_at)，避免仅分区表加宽主键。数据完全一致；季度 RANGE COLUMNS 分区和 p_future，分析副本没有业务 FK，也不声称数据库保证 id 单列唯一。

| 案例/阶段 | 普通表 P50 ms | 分区表 P50 ms | 实际选中分区 |
|---|---:|---:|---|
| 七月范围 / baseline | 619.246 | 200.644 | p3 |
| 七月范围 / composite | 659.009 | 185.085 | p3 |
| 七月范围 / covering | 30.552 | 42.982 | p3 |
| 深 OFFSET / covering | 138.449 | 277.778 | p1,p2,p3,p4,p_future |
| keyset / covering | 4.694 | 2.056 | p1 |
| 仅 id 无时间 / covering | 1.897 | 2.062 | p1,p2,p3,p4,p_future |

无适合范围索引时，季度裁剪使基线访问行数从 1,000,000 降为 251,602；优化后普通表反而更快。分区裁剪由实际谓词与优化器决定，不能把分区等同于索引、分库或通用加速。

## 资源与结论边界

百万运行最终窗口各保留 204 个 runner 和容器样本。runner 进程树 RSS 峰值 94,433,280 bytes，CPU 样本峰值 100.8%；实验容器内存估算峰值 640,260,505 bytes，CPU 样本峰值 255.08%（多核汇总可超过 100%）。首次 CPU 无基线记录 null；原始采样见 resources.jsonl。Windows 进程树 RSS 与 Docker Linux VM 内存口径不同，不相加、不归因到单条 SQL。MySQL Threads_connected/Threads_running、Questions 和配置为整个实验实例快照，包含监测，不是该案例的专属连接数/QPS。

目前证据支持先调整访问路径、投影与分页，再按真实工作负载评估空间/写成本。尚无生产 SLA、持续写入、多租户倾斜、跨节点容量或故障恢复数据，不能因为百万行就引入分库分表。分片还需要路由键、全局唯一标识、跨片查询/事务、扩容迁移、一致性与备份恢复设计；本阶段没有实现这些基础设施。100k 和显式 opt-in 10m 路径有参数/安全测试，本次正式执行的是 10k 与 1m，未声称 10m 性能。

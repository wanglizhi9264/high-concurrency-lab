## 环境和请求模型
主机CPU AMD Ryzen 7 4800H（8核16线程）；Docker分配16 CPU、16699256832字节内存。
MySQL镜像 mysql@sha256:76f0358884cb92d9a086d24e5671c38048d3fef40f2588703d73eb55392d6b69。
MySQL 8.4，独立 Docker 实例，默认 InnoDB buffer pool，详细版本/隔离级别见每个JSON的 environment。Python/SQLAlchemy/asyncmy 客户端在 Windows；loopback TCP，经 Docker Desktop。
单客户端、并发1、固定数据；每条查询预热1次、计时7次，随后真实 EXPLAIN ANALYZE。暖缓存，不刷新buffer pool，无并发写入。每规模1000用户100商品，两明细/订单，seed=20261023，batch=1000。
采样量较小，P95/P99仅为7次样本线性插值，不代表生产尾延迟。CPU/内存利用率未采样（null），记录连接数/配置内存；串行QPS不等于并发API RPS。

## 百万订单的原始深分页计划
基线：
```text
-> Limit/Offset: 20/800000 row(s)  (cost=100582 rows=20) (actual time=519..519 rows=20 loops=1)
    -> Sort: lab_order.created_at DESC, lab_order.id DESC, limit input to 800020 row(s) per chunk  (cost=100582 rows=996441) (actual time=469..498 rows=800020 loops=1)
        -> Table scan on lab_order  (cost=100582 rows=996441) (actual time=0.396..149 rows=1e+6 loops=1)
```
优化后的OFFSET：
```text
-> Limit/Offset: 20/800000 row(s)  (cost=66154 rows=20) (actual time=185..185 rows=20 loops=1)
    -> Covering index scan on lab_order using ix_order_time (reverse)  (cost=66154 rows=800020) (actual time=0.612..163 rows=800020 loops=1)
```
优化后的keyset：
```text
-> Limit: 20 row(s)  (cost=85772 rows=20) (actual time=0.63..0.635 rows=20 loops=1)
    -> Filter: ((lab_order.created_at < TIMESTAMP'2025-01-01 04:48:00') or ((lab_order.created_at = TIMESTAMP'2025-01-01 04:48:00') and (lab_order.id < 286942)))  (cost=85772 rows=422679) (actual time=0.629..0.633 rows=20 loops=1)
        -> Covering index range scan on lab_order using ix_order_time over (created_at < '2025-01-01 04:48:00.000000') OR (created_at = '2025-01-01 04:48:00.000000' AND id < 286942) (reverse)  (cost=85772 rows=422679) (actual time=0.626..0.628 rows=20 loops=1)
```

## 结论与局限
- 支持“合适复合索引减少用户时间排序和深页读取工作量”的假设；全量排序转为按索引逆序访问。
- OFFSET即使有索引也需跳过800000条；已知边界的keyset只取20条，但为了随机定位该边界，本实验另花一次OFFSET成本，不能忽略。连续翻页可直接复用上页游标。
- 小规模by_user/user_time或邮箱wall time可能没有变快，甚至变慢；loopback/客户端/调度噪声与优化器选择影响结果。原始数据如实保留，不筛掉不利样本。
- 邮箱只有1000用户，索引将访问行数从1000变为1，但wall time不必有显著改善；主键始终访问1行，作为稳定性对照。
- 新增索引占用空间并带来写入维护成本；本次未对优化后写入、并发负载、冷缓存、不同分布进行对照，不作扩展结论。
- 基线和优化有前后顺序，buffer pool状态无法完全一致；一次数据集/7次样本仅是教学基线，应通过多轮独立环境验证推广性。
- 所有query成功样本error_rate=0；若查询失败测量中止并不写成功报告，不将缺失实验报告算作0错误。

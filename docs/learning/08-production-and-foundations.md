# 08 从学习台到真实开发：清楚知道还有哪些门

## 问题与解释

本章是缺口说明和设计练习，不代表已实现。数据库白名单保证程序不误写实验库；认证回答“你是谁”，授权回答“你能否操作这张订单”。这三个边界不同。当前API没有完整登录与订单归属权限，不能凭本地实验通过就对公网开放。

最小权限设计：认证层产生可信 current_user；Service查询订单并验证归属，管理员另有明确角色；客户端提交的 user_id 不能证明自己身份。密码保存专用慢哈希而不是明文/普通SHA；选一种Session或Token方案，定义过期、退出和撤销。401表示未通过身份校验，403表示身份已知但无权；是否用404隐藏对象存在性要统一约定。CORS只是浏览器跨源约束，不是服务端权限系统。

部署基础是一个可重现闭环：依赖安装→配置→显式迁移→启动→探针→小范围验证→出错回滚。反向代理/TLS负责入口；API与worker要有独立进程管理与停止策略。当前已有非root Dockerfile和CI，但没有完整生产自动发布。迁移回滚也不等于业务数据可逆，删除列的损失不能靠旧代码恢复。

MySQL卷持久化不等于备份。备份至少要恢复到全新隔离目标，校验行数、关键约束与业务结果。RPO问最多能丢多久数据，RTO问多久恢复服务；应按业务目标决定备份频率与恢复步骤。binlog可用于时间点恢复，但不能替代完整备份与实际演练。Redis RDB/AOF、内存淘汰要知道其作用；本项目Redis不承担订单事实，不必先搭Cluster。

## 动手操作

无需修改服务，先写一张订单访问决策表：匿名/本人/其他用户/管理员分别能否读取、取消；再写三个未来测试的输入与预期状态。不要在真实账号上做越权实验。

运行 `uv run pytest tests/unit/test_config.py tests/unit/test_end_to_end_safety.py -q`，核对配置必需项与隔离保护。再打开Dockerfile和CI，自己圈出“构建、测试、发布”哪些实际存在，不执行新的公网部署。

算法单独练：哈希查重、队列、二分、排序、树的BFS/DFS、堆取TopK、双指针/滑窗和基础动态规划。每题能解释复杂度及边界，业务中可联系幂等键查询/任务排队，但不要重写数据库索引来练树。

## 预期现象

现有配置测试通过，只能证明所测约束；不会凭空增加认证。未来最小授权验收应包含：未登录不能写、其他用户不能操作、本人能操作、客户端伪造user_id无效。这些是待实现标准，当前没有对应安全保证。

## 反例

“用了JWT就安全”忽略签名校验、失效、权限和泄露；“用了Docker就能上线”忽略配置、入口、持久化、进程恢复与监控；“代码回滚就行”忽略Schema兼容性；“备份命令成功”不证明能够恢复。

## 自测与答案

问：当前项目能代替所有面试基础吗？答：不能。操作系统调度/虚拟内存、TCP/HTTP基础、算法编码仍需单独练；用项目问题检验理解，不增加无关组件。

问：下一步优先引入什么框架？答：先明确真实缺口及验收，不预选框架。认证归属、缓存写一致性、过载保护、运行恢复各做独立规格，比立即拆微服务更契合当前系统。

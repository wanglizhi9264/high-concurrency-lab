# 如何把这个项目继续维护清楚

## 改之前先写一句话

例如“首次失败后等待0.2秒再投递，非法业务前提不重试”。如果一句话同时出现读Redis、更新库存、返回JSON，先拆职责。不要从“我要加某种设计模式”开始。

| 改什么 | 去哪里 | 应保留的边界 |
|---|---|---|
| HTTP状态/输入输出 | api/routes、schemas | Service不依赖Response对象 |
| 事务与工作顺序 | services | 谁开事务谁决定提交/回滚；Session不跨任务共享 |
| 固定绑定SQL | repositories | 参数化、正确索引、正确行锁顺序 |
| 可独立解释的业务规则 | domain | 不读时钟、网络、随机源；输入显式、输出小而明确 |
| Redis原子条件 | cache Lua | token与generation检查必须与写入原子执行 |
| 图表/展示 | frontend | Recorded/Live/Simulation区别不能抹掉 |

CacheTtl 是实际过期规则，failure_decision 是实际失败决策，不是可插拔策略框架。规则只有一个实现时，函数/不可变值比类注册器更清楚。将来确有第二种业务策略，再按需求设计接口。

## 审查时画三条线

1. **事务线**：订单和库存是否同一事务？receipt与终态是否一起提交？未知提交是否被误报为失败？
2. **所有权线**：谁持有池、Session、lease？退出时如何关闭？旧worker是否仍可能写结果？
3. **观测线**：指标从哪里来、单位是什么、是否嵌套？未知是否仍为null？

注释解释“为什么”，不要复述语法。好例子：“1062后退出旧事务，避免RR快照看不到赢家”；坏例子：“这里查询订单”。变量不要连续承担输入DTO、ORM实体、HTTP结果三个身份。

## 改完怎么验

先规则边界，再调用链回归；涉及锁/Lua/事务，真实MySQL/Redis测试不可被mock替代。测试检验业务后果，而不是只断言“调用了某函数”。先运行 `uv run python scripts/verify_learning_docs.py`、`uv run python scripts/verify.py`；真实测试依对应指南显式开启。运行性能实验时不同时构建或跑其他基准。

文档要同步更新源文件名、调用顺序、失败条件、实际操作及未实现能力。源码相对链接不写临时行号，减少漂移；文档自测不凭记忆承诺本机性能。历史测量文件不修改，必要的新测量另建run。

## 交付标准

新分支→Specify/Plan/Tasks→只读Analyze→实现→实际验证→只读Converge→PR。PR说明问题、行为、验证和限制；未执行结果留待办。CI通过不等于生产恢复已验证。避免“大量代码重排+新业务+新框架”挤进同一改动，使学习者无法理解为什么变。
